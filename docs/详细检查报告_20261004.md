## 一、发现并修复的问题

### 1.（重要）`/api/identify` 工况自动识别与 `/api/stats` 系统状态端点丢失

- **发现方式**：把 稳定性压测.py 引用的端点清单与当前 API 实现的端点逐一比对；
- **根因**：早期 main 侧"服务API v2.1"（4903f0f）含工况自动识别（8 维统计特征 +
  同相位前缀最近邻），第二轮分支合并时被分支版本覆盖丢失——压测一跑这两个路径
  就会记错误、"0 错误=PASS"的验收项必然失败；
- **修复**：从 git 历史 4903f0f 找回全套实现（特征提取/加权距离/前缀参考/
  置信度），适配当前架构（回放线程私有停止事件、校验后行、窗口加锁）；
  `/api/stats` 的表行数查询改为字面量白名单（原 f-string 不符合安全规范）；
  首页接口清单补两个入口；
- **验证**：进程内识别引擎（回放卡阻 4 秒 → 识别"卡阻"置信度 0.99）；
  **稳定性压测 1 分钟快速模式：816 请求 0 错误、识别 48/48 全对、PASS**；
  identify/stats 延迟 p95 ≈20ms。

### 2.（隐患）工单自动编号用字符串排序取最大值

- **场景**：`ensure_work_order` 用 `max(work_order_id)` 字符串比较——工单号过了
  WO-2026-999 之后，字符串序仍认为 999 最大，新号永远生成 1000 与既有冲突，
  告警自动开单会卡死；
- **修复**：改为 `max(split_part(work_order_id,'-',3)::int)`（正则限定纯数字序号），
  数值比较；当前库最大 047，属提前排雷。

### 3.（残留）alarm_event 表 140 行测试审计记录

- **来源**：第二轮幂等测试导入告警演示数据时，超阈入库触发器自动写入
  （source='仿真-幂等测试'），测试清理只删了 timeseries 没删审计表；
- **处理**：已清理（alarm_event 766 行全为正式数据）；二轮测试脚本的清理块
  补上审计表清理，防止再跑再残留。注：v_fault_episodes 已改基于 timeseries
  计算，该残留不影响任何功能，属数据卫生问题。

## 1. 任务定位与总体设计

本项目三人分工：A 负责 18 号道岔三维模型与仿真数据，B 负责数据管道与数据库，C 负责网页端可视化。B 线的任务是把"数据"从产生到消费的整条链路打通并保证可信：上游接仿真数据（当前为脚本生成的四工况数据集，后续替换 A 的 UM 仿真输出），下游同时供给三类消费方——C 的网页（文件/WebSocket/HTTP 三通道任选）、PostgreSQL 数据库（七表存档与分析）、以及运维决策层（健康度评估、告警、工单、故障诊断）。

链路总览：

```
四工况仿真数据集（20测点 × 100行 × 0.1s，固定种子可复现）
        │  文件直读（契约默认）      WebSocket推送（0.1s实时）     HTTP服务API（CORS全开）
        ├──────────────────────────┼──────────────────────────┐
        ▼                          ▼                          ▼
   C 网页联调                 C 页面实时驱动            监测/健康度/工单/诊断/识别
                                   │
                                   ▼
              PostgreSQL（7表+4视图+1触发器，幂等入库、自动审计、只读账号）
```

任一通道故障可降级退回本地 JSON 文件，不阻塞交付（接口契约约定）。

## 2. 数据契约：三方协作的基石

以《数据格式约定》冻结基础 3 字段（time、switchRailDisp1、pointRailDisp1，0.1s 步长），v2.0 草案增补 17 个可选测点字段（电流/功率/锁闭/密贴/牵引力/振动/磨耗/轮轨力/轨温等，共 20 测点），并约定前向兼容规则：**消费方必须忽略未知字段**——将来数据源升级，C 的页面无需改一行代码。告警阈值存于数据库测点表（尖轨位移 150mm、心轨位移 100mm），前端"超限变红"、服务端判定、监视器标红三方同源。

## 3. 数据库设计与实现（PostgreSQL 17）

选型 PostgreSQL：单实例同时承担关系数据（构件/测点/工单）与时序数据（时序表），预留 TimescaleDB 扩展路径（建库脚本自动检测，未安装则按普通表运行）。

**七张表**：component 构件（9）、measurement_point 测点（20，字段↔测点编码↔3D 节点映射）、timeseries_data 时序（34000 条，主键(测点,时间戳)保证**幂等入库**——重复导入自动跳过）、work_order 工单、realtime_value 实时值（每测点一行，0.1s 刷新）、alarm_event 告警审计、health_score/maintenance_log 运行存档。

**数据库层三道防线**：
1. **告警审计触发器**：数据一入库即比对阈值自动留痕（(测点,时间戳) 唯一约束防重），当前累计 696 条——应用层遗漏也不丢记录；
2. **四个分析视图**：实时值联表、超阈明细、数据源统计、数据质量（窗口函数检测时序断点）；
3. **只读账号 turnout_read**：队友 pgAdmin 直连只读，杜绝误写。

**性能实测**（体检脚本 EXPLAIN ANALYZE）：单测点历史查询 0.099ms 走主键索引；跨表超阈统计 1~5ms；缓冲缓存命中率 100%。全表全列中文注释（COMMENT ON），数据库即文档。

## 4. 服务层 API（FastAPI）

15 个接口覆盖"监测—评估—告警—工单—维修闭环—诊断—识别"完整服务链：实时值/告警/健康度/工单看板/历史查询/测点与模型节点映射（/api/model，C 接 3D 模型的一站式对照表）/四工况回放注入/维修闭环/诊断建议/工况自动识别/系统状态；另设 POST /api/ingest 统一数据直推接口（传感器/仿真 JSON 入库，未知字段忽略回显），为真实传感器接入预留标准入口（MQTT 主题设计亦已在契约中预留）。

工程化措施：数据库连接池（替代每请求建连）、CORS 全开（C 页面跨源直调）、数据库掉线返回 503 附排查提示、历史查询 limit 钳制、浏览器直开诊断/状态接口自动渲染网页版（内容协商，程序调用仍返回 JSON）。

## 5. 健康度评估与工况自动识别

**健康度评分**：可解释规则模型——稳态门（电机运行中只判过程类故障，转换结束后才判结果类故障，避免过渡态误报）+ 扣分制（过流 -30、锁闭失败 -35、转换中断 -30 等），四档等级（优/良/预警/故障）。告警自动生成工单（同测点同问题去重），维修闭环后系统自动重演正常转换复测，健康度回升形成完整闭环。

**工况自动识别**（本文方法亮点）：将回放窗口压缩为 8 维可解释统计特征（终点位移、电流均值/峰值/末段电流、锁闭末态、密贴末态、密贴抖动、位移全程变化），与四个工况参考特征做**同相位前缀加权最近邻**匹配——回放进行到第 L 行即与各工况前 L 行比较，中途即可识别；置信度按"与次近距离之比"计算，两工况前段数据本就相同时置信度诚实趋近 0（数据边界如实呈现）。实测 4 工况 × 3 采样相位 **12/12 全对**（置信度 0.99）；3 分钟连续回放压测中 **154/154（100%）**。答辩口径：可解释的统计特征识别，非深度学习。

## 7. 协作机制

接口契约版本化管理（v1.0 冻结基础字段，v2.0 草案群确认生效）；《接口对接指南》提供 A/C 的代码级对接样例；共享 GitHub 仓库三人协作（B 线成果含全部脚本、文档、可复现数据集与导出快照）；"谁改谁通知、文档同步升版本号"贯穿全程。

## 8. 局限与展望（诚实边界）

当前为仿真数据驱动的验证原型：数据由物理量纲合理的脚本生成（固定随机种子可复现），非真实传感器实时流；单道岔（T01）；健康度为规则模型、识别为统计方法，均非机器学习。已预留的升级路径：UM 仿真数据经同一转换脚本无缝替换（契约字段不变）；真实传感器经 POST /api/ingest 或 MQTT 接入（主题设计已定）；TimescaleDB 安装后重跑建库脚本即转为 hypertable。
